## 0. 对初版方案的修正

初版技术方案有 5 处需要纠正，本文档以修正后的结论为准：

| # | 初版说法 | 问题 | 修正结论 |
|---|---|---|---|
| C1 | 手写引擎用 `smooth-signature` + 自建 Pointer 层 | 该库自带事件绑定、单 Canvas 全量重绘，与「三层 Canvas 增量绘制」「coalesced 补点」「笔模式过滤」三者直接冲突，两套事件系统会互抢 | **弃用该库，自建渲染核心**；只借鉴其「速度→线宽」笔锋思路 |
| C2 | 首笔延迟压至 **14ms** | 单帧 `rAF` 间隔就是 16.7ms，14ms 不是可达成也不是可测量的口径 | 改为 **pointerdown → 首帧绘制完成 P95 ≤ 32ms**，并在文档中声明这是代理指标（不含合成上屏耗时） |
| C3 | `gridType` 含 `mixed` | 语义未定义，且与「V1.0 只做固定几种格子」的范围冲突 | V1.0 为 `tianzi` / `mizige` / `pinyin`，`mixed`（混合排版）延后到 V1.1 |
| C4 | 四线三格「外框四条水平线，中间两条虚线」 | 未指明哪条是基线；拼音教学的落笔基准是第 3 线 | 明确：第 3 线为**基线（较深实线）**，第 2 线为虚线，1/4 线为浅实线 |
| C5 | 每页一条 IndexedDB 记录 | 单页笔迹可达数 MB，页列表加载会搬运整本数据 | **元数据与笔迹分表**：`pages` + `contents`，列表只读 `pages` |

## 1. 技术选型

| 层级 | 选型 | 理由 |
|---|---|---|
| 框架 | **Vue 3 + Vite + TypeScript** | 构建快、开发期 HMR 友好；PWA 插件成熟 |
| 状态 | Pinia（仅页面元数据/UI 状态） | 笔迹与渲染状态放在引擎类的普通字段里，不进 Vue 响应式，避免代理开销 |
| 手写渲染 | **自研**（Pointer Events + rAF + 三层 Canvas） | 见 C1；可控采样、防误触、增量绘制 |
| 格子绘制 | Canvas 2D 自绘 | 纯线条，任意分辨率清晰，无图片资源 |
| 字体 | 开源楷体（建议 LXGW WenKai）**子集化为 woff2** | 描红必须用楷体字形；子集化控制体积 |
| 存储 | IndexedDB（`idb` 轻量封装） | 结构化、事务、容量足够 |
| 离线和分发 | `vite-plugin-pwa`（Workbox `generateSW`） | 预缓存 App Shell，一次配置 |
| 手势/工具 | 无第三方手势库 | `touch-action: none` 之后不需要任何手势库 |

**明确不引入**：`smooth-signature`、`signature_pad`、任何绑定 `touchstart` 的手写库、任何 UI 组件库。

## 2. 架构分层

```
┌─────────────────────────────────────────┐
│ Layer 3  UI（DOM）                        │  工具栏 / 页列表 / 弹层
├─────────────────────────────────────────┤
│ Layer 2  当前笔画 Canvas（live）           │  本帧新增线段，增量绘制，不清屏
├─────────────────────────────────────────┤
│ Layer 1  已完成笔迹 Canvas（ink）          │  抬笔时一次性提交
├─────────────────────────────────────────┤
│ Layer 0  格子 + 字帖底字 Canvas（grid）    │  仅布局变化时重绘
└─────────────────────────────────────────┘
```

- 三个 `<canvas>` 元素绝对定位叠放，尺寸一致，`z-index` 递增。
- 都使用 `width/height = CSS尺寸 × dpr` 的物理像素后备存储，绘制前 `ctx.scale(dpr, dpr)`，之后**所有绘制代码只用 CSS px 逻辑坐标**。
- 层职责隔离：格子层永远不重绘笔迹；笔迹层永远不重绘格子；UI 层在 DOM 里，Canvas 上不做按钮。
- `touch-action: none` + `user-select: none` 加在书写容器上，同时在 `pointerdown` 里 `preventDefault`。

## 4. 输入采集

### 4.1 事件与补点

```ts
// core/input/PointerInput.ts
el.addEventListener('pointerdown', onDown, { passive: false })
el.addEventListener('pointermove', onMove, { passive: false })
el.addEventListener('pointerup', onUp)
el.addEventListener('pointercancel', onUp)
el.addEventListener('contextmenu', e => e.preventDefault())
```

`pointermove` 必须取出合并事件：

```ts
function onMove(e: PointerEvent) {
  if (!accept(e)) return
  e.preventDefault()
  const list = e.getCoalescedEvents?.() ?? [e]
  for (const ev of list) pushPoint(ev)
}
```

- `getCoalescedEvents` 在 Chrome 58+ 可用，作为可选链降级。
- **不使用 `getPredictedEvents()`**：预测点会带来「笔迹抖动/回拉」，儿童书写场景收益不抵风险。
- 坐标系换算统一走一个函数，避免多处重复推导：

```ts
const rect = el.getBoundingClientRect()
const x = (e.clientX - rect.left) / rect.width   // → 0..1 归一化
const y = (e.clientY - rect.top) / rect.height
```

### 4.2 坐标约定（重要）

**笔迹点存储为归一化坐标 `0..1`**，相对书写区尺寸。

- 好处：屏幕旋转、分屏、不同机型下笔迹按比例缩放，不会因为 `cols` 变化而错位到别的格子里。
- 渲染时：`px = x * cssWidth`，`py = y * cssHeight`。
- 代价：极端长宽比变化时字形会被拉伸。V1.0 接受此行为（PRD A18 只要求「位置正确、数据不丢」）。

> 不采用「绝对 CSS px + 变更时批量换算」：需要在每次布局变化时重写整页数据，失败即数据损坏，风险更高。

### 4.3 采样过滤

```ts
const MIN_DIST = 0.8 / rect.width   // 归一化后约 0.8 CSS px
if (dist(p, last) < MIN_DIST) return
```

- 单笔点数上限 2000；达到上限后按 `MIN_DIST × 1.5` 逐级抽稀，不截断。

## 5. 渲染引擎

### 5.1 主循环

```ts
class RenderEngine {
  private dirty = false
  private rafId = 0

  requestDraw() {
    if (this.dirty) return
    this.dirty = true
    this.rafId = requestAnimationFrame(this.frame)
  }

  private frame = () => {
    this.dirty = false
    this.drawLiveIncrement()   // 只画本帧新增的线段
  }
}
```

- `pointermove` 里**只做数据 push + `requestDraw()`**，绝不直接绘制。
- 一帧内可能收到多批点，统一在这里消费。

### 5.2 增量绘制策略

| 层 | 时机 | 方式 |
|---|---|---|
| grid | 初始化 / 布局变化 / 字帖数据变化 | `clearRect` 后整层重绘一次 |
| ink | 抬笔提交、撤销、重做、擦除、加载页面 | 见下 |
| live | 每帧 | **只追加新线段，不清屏**（笔画是叠加的，无覆盖需求） |

抬笔提交：

```ts
commit(stroke) {
  this.painter.paintWhole(this.inkCtx, stroke)   // 整笔一次性画到 ink 层
  this.liveCtx.clearRect(0, 0, w, h)             // 清空 live 层
}
```

> live 层不清屏、只追加，是本方案相对「每帧重绘当前笔画」的关键性能改进：500 点的笔画从每帧 500 次 `stroke()` 降到每帧 2–4 次。代价是启动/换页时必须显式 `clearRect`，需在状态机上保证不漏。

### 5.3 撤销与重做

ink 层是**位图**，无法「反向擦除」，因此撤销需要重建：

```ts
rebuildInk() {
  this.inkCtx.clearRect(...)
  for (const s of this.strokes) this.painter.paintWhole(this.inkCtx, s)
}
```

- 撤销栈 30 步；重做栈在产生新操作时清空。
- 重建耗时与笔画数线性相关。**基准要求**：800 笔页面重建 ≤ 150ms；超时则在 UI 上显示极短的忙碌态，不阻塞输入事件。
- 备选优化（暂不实现，留作 P2）：每 50 笔缓存一张 `ImageBitmap` 快照，重建时从最近快照重放。内存代价约 `宽×高×4×快照数`，需实测。

### 5.4 可变线宽绘制

不做轮廓多边形，采用**分段描边 + round cap/join**，在采样点足够密时视觉与轮廓法无差别，且实现简单、每段独立代价低。

```ts
// core/engine/StrokePainter.ts
paintSegment(ctx: CanvasRenderingContext2D, a: Pt, b: Pt, width: number, color: string) {
  ctx.strokeStyle = color
  ctx.lineWidth = width
  ctx.lineCap = 'round'
  ctx.lineJoin = 'round'
  ctx.beginPath()
  ctx.moveTo(a.x, a.y)
  ctx.lineTo(b.x, b.y)
  ctx.stroke()
}
```

- 段与段之间的圆形端帽天然重叠，不会出现断口。
- `ctx.state`（`strokeStyle`/`lineWidth`）在同一笔内变化，无法用 `Path2D` 批量合并——这是可变线宽的固有代价，通过「仅 live 层增量绘制」抵消。

### 5.5 平滑与去抖

- **平滑**：不对点做全局滤波（会引入延迟），改用「中点二次贝塞尔」在绘制时平滑：

```ts
// 用前后点的中点作为曲线端点，原始点作为控制点
const mid1 = midpoint(p0, p1), mid2 = midpoint(p1, p2)
ctx.quadraticCurveTo(p1.x, p1.y, mid2.x, mid2.y)
```

- 线宽仍按 `p0→p1` 的距离与时间差计算，两者解耦。
- **去抖**：仅在归一化距离小于阈值时丢弃点；不做「防手抖移动平均」，避免儿童慢写时笔画「跟不上手」。

### 5.6 线宽模型

```ts
// core/stroke/WidthModel.ts
// 速度单位：CSS px / ms
const speed = dist(a, b) / Math.max(dt, 1)
const t = clamp((speed - MIN_SPEED) / (MAX_SPEED - MIN_SPEED), 0, 1)
const width = maxW - (maxW - minW) * t        // 慢 → 粗，快 → 细
```

- 速度做 EMA 平滑（`α = 0.3`），避免线宽在相邻段之间跳变。
- `minSpeed` 默认 0.15、`maxSpeed` 默认 2.5，需在真机调参。

**压感优先**：

```ts
// 设备探测：连续 20 个点的 pressure 方差 < 1e-6 且恒为 0.5 → 判定无压感
const usePressure = pressureVariance > 1e-6
const width = usePressure
  ? minW + (maxW - minW) * pressure
  : speedBasedWidth()
```

> 部分安卓设备的主动笔恒返回 `0.5`，如果不做探测会得到一条死线宽的「铁丝」，这正是 PRD 风险 R5 的落地对策。

## 6. 笔模式（防误触）

```ts
// core/input/PointerInput.ts
private penMode = false

private accept(e: PointerEvent): boolean {
  if (e.pointerType === 'pen') {
    if (!this.penMode) this.onPenModeChange(true)   // 首次检测自动进入
    this.penMode = true
    return true
  }
  return !this.penMode        // 笔模式下丢弃 finger / mouse / touch
}
```

要点：

1. **过滤只发生在书写区的监听器里**。UI 层是 DOM 元素，不经过这段逻辑，因此手指点按钮天然可用。
2. `pointercancel` 与 `pointerup` 也要走 `accept`，否则笔模式下会产生「只按下没抬起」的悬空笔画。
3. 状态存在 `notebook` store，切页不重置，退出只能通过 UI 按钮。
4. 按钮文案在笔模式开启时高亮（PRD F3.2 的可见性要求）。
5. 多指同时按下：只跟踪第一个被 `accept` 的 `pointerId`，其余 `pointerId` 全部忽略，直到该 `pointerId` 抬起（PRD F2.3）。

## 7. 格子渲染

### 7.1 布局计算（纯函数）

```ts
// core/layout/GridLayout.ts
export interface GridLayout {
  type: GridType
  margin: number          // 四周留白
  originX: number         // 内容区左上角
  originY: number
  cols: number            // 方格类（田字格/米字格）列数；四线三格固定为 1（无列概念）
  rows: number
  cellSize: number        // 方格类边长 / 四线三格的单格高 u
  rowPitch: number        // 方格类 = cellSize；四线三格 = 4u
  contentWidth: number    // 实际占用宽度
  contentHeight: number   // 实际占用高度（末行不含行间距）
}
```

**田字格 / 米字格**（两者几何完全一致，共用同一套计算，只在内线绘制上区分）

```ts
const MARGIN = 16
const TARGET_CELL = 96            // 期望边长
const availW = w - MARGIN * 2
const cols = clamp(Math.round(availW / TARGET_CELL), 4, 12)
const cellSize = availW / cols    // 横向铺满，保证整数格、无半格
const rows = Math.max(1, Math.floor(availH / cellSize))
const offsetY = (availH - rows * cellSize) / 2   // 垂直居中留白
```

**四线三格**

单格高 `u` 必须由**页面高度**反解，不能由宽度推算（宽度只决定一行能写多少个字母）。

```ts
// 先按目标行距定行数，再令 rows × 4u − u 恰好填满可用高度
const targetRows = clamp(Math.round(availH / 100), 4, 12)
const u = clamp(Math.floor(availH / (targetRows * 4 - 1)), 20, 32)
const rowPitch = u * 4                                   // 条带 3u + 间距 1u
const rows = Math.max(1, Math.floor((availH + u) / rowPitch))
const contentHeight = (rows - 1) * rowPitch + u * 3      // 末行无行间距
```

> **实现修正**：初版公式 `u = clamp(round(availW / 28), 22, 36)` 是宽度驱动的，
> 实测在 11 寸横屏只填满 85% 高度、页面下方留下近百像素空白，且 `u` 会被钳到下限 20。
> 改为高度反解后同类场景利用率达 97%。另注意 `u` 必须**向下取整**：向上取整会因每行多占
> 1px 而把行数挤掉一行，反而损失近一整行的高度。

- 横竖屏切换 / `ResizeObserver` 触发时重算，**重置 `cols` 与落笔坐标映射**。
- 已是字帖页时 `cols` 由字库固定，不从当前页继承（PRD F8.1）。

### 7.2 绘制

```ts
// 田字格：外框实线 + 十字虚线；米字格：同一份代码再加两条对角线，描边次数不变
ctx.strokeStyle = LINE_COLOR        // #d98b8b
ctx.lineWidth = 1                   // CSS px，已由 ctx.scale(dpr) 处理
strokeRect(...)
ctx.setLineDash([4, 4])
miterCross(...)                     // 横中线 + 竖中线（更浅色）
ctx.setLineDash([])
```

```ts
// 四线三格：4 条等距水平线
line1 实线 浅色
line2 虚线 浅色        // 中格上沿
line3 实线 较深色      // 基线，用 LINE_COLOR_STRONG
line4 实线 浅色
```

- 一个像素的线要清晰，必须落在**半像素网格**上：`x + 0.5`（在 dpr 缩放后按 `1/dpr` 对齐）。
- 线条颜色与虚线节奏抽成常量表，便于统一调整柔和度。

### 7.3 描红底字

```ts
// core/engine/CopybookRenderer.ts
ctx.font = `${size}px WenKai, serif`
ctx.textAlign = 'center'
```

| 类型 | 基线 | 字号 | 透明度 |
|---|---|---|---|
| 拼音 `demo` | `alphabetic`，`y = 第 3 线` | `u × 2.14` | 0.55 |
| 拼音 `trace` | 同上 | 同上 | 0.15 |
| 汉字 `demo` | `alphabetic`，`y = 格中心 + 该字墨迹中心偏移` | `cellSize × 0.98` | 0.55 |
| 汉字 `trace` | 同上 | 同上 | 0.15 |

两个系数的来源（都不是拍脑袋）：

- **拼音 2.14**：字体 `OS/2.sxHeight = 468`，unitsPerEm = 1000，即 x-height = 0.468em。
  要中格字母高度恰好等于 `u`，字号必须取 `u / 0.468 ≈ 2.14u`。换字体必须重算。
- **汉字 0.98**：实测该字体满框字（三/四/五）墨迹高度 ≈ 0.73em，
  取 0.98 使墨迹约占格边长 72%，四周留白均匀。

汉字底字的定位**不能用 `textBaseline = 'middle'`**：汉字字形在 em 框里上紧下松，
实测整体偏低约 6px。正确做法是读该字的 `actualBoundingBoxAscent/Descent`，
把墨迹中心对齐到格中心——实测残留误差 ≤ 0.5px。

`PINYIN_FONT_SCALE` 是**校准常量**，初值取 `1.82`（依据楷体 x-height ≈ 0.55em），必须在真机上以 `a / o / e` 为基准目视校准到 PRD 要求的 ≤ 2px 误差。此常量写入 `gridConfig.ts` 并在 README 注明「改字体必须重新校准」。

## 8. 字体方案

描红必须使用手写规范字形，默认黑体会教错笔形。

| 项 | 决策 / 实测 |
|---|---|
| 字体 | LXGW WenKai v1.530（SIL OFL 1.1，可商用），许可证随字体放在 `public/fonts/OFL.txt` |
| 获取途径 | GitHub Release 下载被网络环境阻断（HTTP/2 framing / 空响应），改从 npm `lxgw-wenkai-webfont@1.7.0` 取分片 |
| 子集化 | 该包的 regular 体按 unicode-range 拆成 97 个 woff2 分片，本应用字符只命中 14 个；用 fontTools 合并后子集化 |
| 体积 | **12.1 KB**（110 字，含拼音声调字符），远低于 600KB 预算 |
| 加载 | `FontFace` 异步加载，不阻塞首屏；加载完成后重绘格子层 |
| 降级 | 加载失败时回退 `Kaiti SC / STKaiti / serif`，控制台告警 |


## 9. 擦除命中检测

```ts
// core/hit/EraseHitTest.ts
const TOLERANCE = 12   // CSS px

function hitTest(p: Pt, strokes: Stroke[], toPx): Stroke | null {
  let best: { s: Stroke; d: number } | null = null
  for (const s of strokes) {
    if (!bboxContains(s, p, TOLERANCE)) continue        // 包围盒快速剪枝
    const d = minDistanceToPolyline(p, s, toPx)
    if (d <= TOLERANCE && (!best || d < best.d)) best = { s, d }
  }
  return best?.s ?? null
}
```

- 先做包围盒剪枝（O(n) 但要遍历，成本极低），再做逐段点线距离。
- 归一化坐标 → CSS px 后再算距离，容差才是真实物理量。
- 只删最近的一笔，不做连擦（PRD F4.3）。

### 10.1 IndexedDB Schema

```ts

// v1
pages:    keyPath 'id',        index 'updatedAt'

```

**为什么分两张表**：单页 800 笔约 1–3MB，200 页的 `pages` 若内联 `strokes`，打开页列表会反序列化几十 MB。分表后列表只读轻量元数据（每页 < 2KB）。

### 10.2 保存策略

```
抬笔 → markDirty(pageId)
        ├─ debounce 800ms          → flush
        ├─ 未落盘时长 > 4000ms     → flush（连续书写时的兜底上限）
        └─ pagehide / visibilitychange(hidden) / 切页 / 导出前 → 强制 flush
```

```ts
// store/SaveQueue.ts
class SaveQueue {
  private pending = new Set<string>()
  private timer = 0
  private firstDirtyAt = 0

  markDirty(id: string) {
    this.pending.add(id)
    if (!this.firstDirtyAt) this.firstDirtyAt = performance.now()
    clearTimeout(this.timer)
    this.timer = setTimeout(() => this.flush(), DEBOUNCE_MS)
    if (performance.now() - this.firstDirtyAt > MAX_WAIT_MS) this.flush()
  }

  async flush() { /* 事务内写入 contents + pages 元数据 + 缩略图 */ }
}
```

- flush 一次写三样：`contents.strokes`、`pages.strokeCount/updatedAt`、缩略图（**每页最多每 30 秒重建一次**，避免频繁 `toDataURL`）。
- 笔迹写入用**扁平数组** `[x,y,p,t, ...]`：相比对象数组，JSON/结构化克隆体积约减半，重建 `Float32Array` 更快。

### 10.3 缩略图

## 11. 导出与导入

### 11.1 单页 PNG

```ts
async function exportPagePng(page): Promise<Blob> {
  await saveQueue.flush()
  const scale = 2
  const c = new OffscreenCanvas(w * scale, h * scale)
  const ctx = c.getContext('2d')!
  ctx.scale(scale, scale)
  ctx.drawImage(gridCanvas, 0, 0, w, h)   // 含字帖底字
  ctx.drawImage(inkCanvas, 0, 0, w, h)
  ctx.drawImage(liveCanvas, 0, 0, w, h)   // 兜底：未提交的当前笔

}
```

- 长边上限 2400px：`scale = Math.min(2, 2400 / Math.max(w, h))`。
- 输出走 `Blob` → `URL.createObjectURL` → `<a download>`。**不要用 `toDataURL`**（大页面下它会同步阻塞主线程，直接违反 PRD 的 100ms 要求）。

### 11.3 导入校验

```
1. JSON.parse  → 失败 → 提示「文件无法解析」
2. app !== 'grid-notebook' → 提示「不是本应用的备份」

```

- **绝不覆盖已有页面**（PRD F7.3）。
- 单页数据超过阈值（如 5MB）时跳过并计入 `skipped`。

| # | 措施 | 目标 |

### 13.1 测量方式

内置**开发模式性能面板**（`?debug=1` 开启，与布局度量共用同一个浮层）：

```ts
// 首笔延迟（代理指标）
onPointerDown: t0 = performance.now()
frame() 中首次 paint 完成后: latency = performance.now() - t0
// 采样 200 次，取 P95
```

```ts
// 帧率
let last = performance.now(), frames = 0, dropped = 0
function tick(now) {
  const dt = now - last; last = now
  if (dt > 32) dropped++
  frames++
  requestAnimationFrame(tick)
}
```

> 明确声明：该指标**不包含**浏览器合成与屏幕刷新，真实上屏约再 +8~16ms。PRD 的 32ms 口径与此一致。

**两个必须避开的度量陷阱**（M2 实测踩到，均已修复）：

| 陷阱 | 表现 | 处理 |
|---|---|---|
| 帧循环只在书写期间运行 | 抬笔后的空闲期被算成一帧，60 FPS 显示成 6 FPS | 帧循环启动时重置帧时钟（`resetFrameClock()`） |
| 落笔计时标记不会自动失效 | 极快的轻点/合成事件在首帧前就结束，标记残留，下一笔沿用旧起点，13ms 报成 318ms | `markPointerDown` 无条件重置起点，不因上一次未收口而跳过 |

### M2 · 手写核心（2026-10-27）

| # | 现象 | 根因 | 结论 |

### M3 · 页面、存储与导出（2026-10-27）

| # | 现象 | 根因 | 结论 |
|---|---|---|---|
| M3-1 | 长时连续书写的 `maxWait` 兜底不生效 | `firstDirtyAt = 0` 既表示「未初始化」又是合法时间戳，导致每次都重新初始化 | 哨兵值改为 `-1`；单测（假定时器从 0 开始）暴露了这个问题 |
| M3-2 | 高分屏导出的图片只画出左上角一块 | 三层画布的后备存储是「CSS 尺寸 × dpr」，直接 `drawImage(layer, 0, 0)` 会按物理像素当用户单位 | 合成时显式传目标尺寸 `drawImage(layer, 0, 0, cssW, cssH)`，并整体 `setTransform(scale, …)` |
| M3-3 | 备份导入中途失败会留下半批页面 | 逐页写入不是原子操作 | 仓储增加 `putPages()`，整批在一个 IDB 事务内完成，任一失败整体回滚 |
| M3-4 | 页列表缩略图裁掉一半、看不懂内容 | `object-fit: cover` 把 16:9 的页面裁进 1.35 的框 | 改为 `contain` + 容器 `aspect-ratio: 1.7` |
| M3-5 | 200 页列表是否够快 | —— | 实测启动 42ms、列表打开 38ms（含 200 张缩略图），预算 500ms |
| M3-6 | 新增米字格 | 米字格 = 田字格 + 两条对角线，若单独实现会与田字格出现格数/格尺寸漂移 | 布局层共用 `layoutSquare(type, …)`，渲染层复用同一条内线路径，米字格只多 `withDiagonals` 分支；描边次数仍为 2 |

**落盘验证方式**：不依赖 `pagehide`/`visibilitychange` 的兜底，而是在抬笔 1.3 秒后直接打开 IndexedDB 读 `contents`，
确认节流队列已独立完成写入（实测 2 笔，首笔 76 个点）。这比「刷新页面看还在不在」更严格，因为刷新会触发强制落盘。
